## 1. 사용자 입력 기반 대표 코스 추천

### 문제

사용자가 장소를 하나씩 탐색하여 코스를 만드는 방식은 선택 피로도가 높고, 전체 이동 흐름을 고려하기 어렵다. 한편 외부 API에서 장소를 실시간으로 조합하면 정제되지 않은 데이터가 추천 결과에 포함되고 외부 서비스 상태에 영향을 받을 수 있다.

### 결정

사용자로부터 도시, 선호 태그, 동행자 유형, 시간대를 입력받고 DB에 저장된 공개 대표 코스 중 적합한 결과를 최대 5개 추천한다.

```text
사용자 입력 검증
→ 선택한 도시의 공개 코스 조회
→ 비활성 장소가 포함된 코스 제외
→ 태그·동행자·시간대·인기도 점수 계산
→ 점수순 정렬
→ 앵커 다양성을 고려해 최종 코스 선정
→ 추천 노출 통계 기록
→ 응답 반환
```

### 결정 이유

- 수집·정제된 장소와 검수 가능한 코스만 추천할 수 있다.
- 외부 API 장애와 응답 속도가 실시간 추천에 직접 영향을 주지 않는다.
- 추천된 코스를 먼저 제공하고 사용자가 세부 장소를 수정하는 흐름으로 선택 피로도를 낮출 수 있다.

### 현재 한계

- 추천 품질이 저장된 대표 코스의 수와 품질에 영향을 받는다.
- 사용자 과거 행동을 반영하지 않는 요청 단위 추천이다.
- 코스 생성과 태깅 자동화는 아직 구현되지 않았다.

## 2. 코스와 장소 태그의 통합 평가

### 문제

코스 태그만 평가하면 코스를 구성하는 식당, 카페, 활동 장소의 세부 특성을 놓칠 수 있다. 예를 들어 코스에는 `쇼핑` 태그만 있지만 코스에 포함된 식당에는 `한식` 태그가 있을 수 있다.

### 검토한 방법

1. 코스 태그만 평가
2. 장소 태그만 합산
3. 코스 태그와 장소 태그에서 가장 강한 근거를 사용

태그를 모두 합산하면 같은 의미의 태그가 여러 장소에 있다는 이유만으로 점수가 과도하게 커질 수 있다.

### 결정

사용자가 선택한 태그별로 코스와 구성 장소의 가중치 중 가장 높은 값 하나를 사용한다.

```text
태그별 최종 가중치
= max(코스 태그 가중치, 앵커 및 일정 장소 태그 가중치)
```

최종 추천 점수는 다음과 같이 구성한다.

| 평가 항목 | 최대 점수 | 설명 |
|---|---:|---|
| 태그 적합도 | 70점 | 코스와 장소에서 얻은 태그별 최댓값의 평균 |
| 동행자 적합도 | 10점 | 친구, 연인, 가족 등 요청 조건과의 적합도 |
| 시간대 적합도 | 10점 | 아침, 오후, 밤 요청 조건과의 적합도 |
| 인기도 | 10점 | 기존 코스 선택 횟수 |

요청 태그의 매칭 정도는 `FULL_MATCH`, `PARTIAL_MATCH`, `POPULAR_FALLBACK`으로 구분한다.

### 결정 이유

- 코스의 전체적인 성격과 구성 장소의 세부 특성을 함께 반영할 수 있다.
- 동일 태그의 중복 합산으로 특정 코스가 과대평가되는 것을 방지한다.
- 추천 응답에서 일치·불일치 태그와 점수 구성을 설명할 수 있다.

### 현재 한계

- 태그 및 가중치 품질에 추천 결과가 크게 의존한다.
- 코스 안에서 해당 태그를 가진 장소의 개수와 일정상 중요도는 반영하지 않는다.
- 데이터가 쌓이면 실제 사용자 행동을 기준으로 가중치를 보정해야 한다.

## 3. 인기도 점수와 콜드 스타트

### 문제

사용자가 태그를 적게 선택하면 비슷한 점수를 가진 후보 코스가 많아진다. 선택 횟수를 그대로 점수에 더하면 오래 운영된 코스가 추천 결과를 독점할 수 있고, 신규 코스는 통계가 없어 불리하다.

### 결정

선택 횟수가 증가할수록 최대 10점에 완만하게 가까워지는 포화 함수를 사용한다.

```text
인기도 점수
= selectionCount / (selectionCount + 20) × 10
```

통계가 없는 신규 코스는 선택 횟수를 0으로 계산한다. 노출·조회·선택 비율은 아직 추천 점수에 사용하지 않고 분석용 데이터로만 수집한다.

### 결정 이유

- 선택 횟수가 0이어도 별도 예외 처리 없이 계산할 수 있다.
- 인기 코스를 우대하면서도 인기도가 최대 10점을 넘지 않아 태그 적합도를 뒤집기 어렵다.
- 표본이 매우 적은 코스의 일시적인 높은 선택률이 추천을 왜곡하는 문제를 피할 수 있다.

### 현재 한계

- 누적 선택 횟수만 사용하므로 오래된 코스가 계속 유리하다.
- 노출 대비 선택 성과를 반영하지 않는다.
- 계절성과 최근 인기도 변화를 반영하지 않는다.

### 향후 개선

충분한 노출 데이터가 쌓이면 다음 지표를 검토한다.

```text
상세 조회율 = viewCount / impressionCount
선택률 = selectionCount / impressionCount
상세 조회 후 선택률 = selectionCount / viewCount
저장률 = saveCount / selectionCount
```

표본이 적은 코스가 과대평가되지 않도록 최소 노출 기준, 베이지안 보정 또는 시간 감쇠를 함께 적용한다.

## 4. 추천 결과의 앵커 다양성

### 문제

총점만 기준으로 상위 코스를 선택하면 동일한 앵커를 사용하는 비슷한 코스가 반복될 수 있다.

### 결정

서로 다른 앵커를 가진 코스를 우선 선택하고 결과가 부족할 때만 같은 앵커의 코스로 남은 자리를 채운다.

### 결정 이유

- 추천 점수 구조를 크게 변경하지 않고도 결과의 체감 다양성을 높일 수 있다.
- 같은 도시 안에서 서로 다른 활동 거점을 비교할 수 있다.

### 현재 한계

- 앵커만 다르고 일정 장소 구성이 유사한 코스는 중복으로 판단하지 못한다.
- 지역 및 장소 조합의 유사도를 정량적으로 계산하지 않는다.

## 5. 추천 조회의 N+1 방지

### 문제

추천 점수 계산에는 코스, 앵커, 일정 장소, 코스 태그, 동행자 유형, 시간대가 함께 필요하다. 코스마다 연관 데이터를 개별 조회하면 후보 수에 비례하여 쿼리가 증가한다.

### 결정

- 코스 조회 시 `EntityGraph`로 필요한 연관 데이터를 함께 조회한다.
- 장소 태그는 전체 장소 ID 목록으로 일괄 조회한다.
- 코스 통계는 전체 코스 ID 목록으로 일괄 조회한다.

### 결정 이유

추천 계산 반복문 안에서 추가 조회가 발생하지 않도록 하여 N+1 문제를 방지한다.

### 현재 한계

여러 컬렉션을 한 번에 조회하면 후보가 많아질수록 조인 결과가 커질 수 있다. 실제 성능 문제가 확인되면 코스 ID를 먼저 제한한 뒤 연관 데이터를 분리된 벌크 쿼리로 조회한다.

## 6. 추천 노출 통계의 동시성 처리

### 문제

추천 목록에 포함된 코스의 노출 횟수를 엔티티의 조회-수정-저장 방식으로 증가시키면 동시 요청에서 갱신 손실이 발생할 수 있다.

```text
요청 A: impressionCount 10 조회 → 11 저장
요청 B: impressionCount 10 조회 → 11 저장

기대 결과: 12
실제 결과: 11
```

추천 결과 여러 개를 각각 조회하고 저장하면 불필요한 쿼리도 발생한다.

### 검토한 방법

1. `CourseStats.recordImpression()`으로 엔티티 상태 변경
2. 낙관적 락과 재시도 적용
3. 비관적 락으로 통계 행 잠금
4. DB의 원자적 증가 연산 사용

### 결정

노출 횟수는 별도의 도메인 규칙이 없는 고빈도 집계값이므로 PostgreSQL의 UPSERT와 원자적 증가 연산으로 처리한다.

```sql
INSERT INTO course_stats (course_id, impression_count)
SELECT id, 1
FROM courses
WHERE id IN (:courseIds)
ON CONFLICT (course_id)
DO UPDATE
SET impression_count = course_stats.impression_count + 1;
```

### 결정 이유

- 동시 요청에서도 증가 값이 유실되지 않는다.
- 최종 추천 코스 여러 개를 한 번의 쿼리로 처리한다.
- 아직 통계 행이 없는 코스는 자동으로 생성한다.
- 락과 재시도 코드를 애플리케이션에 추가하지 않아도 된다.

DDD에서 모든 변경을 반드시 엔티티 메서드로 처리해야 하는 것은 아니다. 코스 공개나 일정 추가처럼 도메인 검증이 필요한 행동은 엔티티가 담당하고, 단순 통계 누적은 저장소가 동시성에 안전하게 처리하도록 역할을 나눴다.

### 현재 한계

- 현재 `impressionCount`는 실제 화면 노출이 아니라 추천 API 응답에 포함된 횟수다.
- 기간별 행동 이력을 남기지 않고 누적값만 저장한다.
- 조회·선택·저장·공유 횟수에도 같은 동시성 정책을 적용해야 한다.

### 향후 개선

- 프론트에서 추천 카드가 실제 표시된 시점에 노출 이벤트 전송
- 나머지 행동 카운터도 DB 원자적 증가 방식으로 통일
- 기간별 분석이 필요해지면 집계 테이블과 별도로 행동 이벤트 저장

## 7. 현재 추천 시스템의 범위

현재 구현은 정교한 머신러닝 추천보다 설명 가능하고 검증하기 쉬운 규칙 기반 MVP에 집중한다.

```text
사용자 선호 태그
+ 코스 전체 특성
+ 구성 장소 특성
+ 동행자·시간대 적합도
+ 선택 횟수 기반 인기도
+ 앵커 다양성
```

추천 점수와 매칭 근거를 응답에 포함하여 결과를 확인할 수 있으며, 노출·조회·선택·저장 통계를 축적해 이후 데이터 기반 추천으로 개선할 수 있는 기반을 마련했다.
