## 1. 사용자 입력 기반 대표 코스 추천

### 문제

사용자가 장소를 하나씩 탐색하여 코스를 만드는 방식은 선택 피로도가 높고, 전체 이동 흐름을 고려하기 어렵다. 한편 외부 API에서 장소를 실시간으로 조합하면 정제되지 않은 데이터가 추천 결과에 포함되고 외부 서비스 상태에 영향을 받을 수 있다.

### 결정

사용자로부터 도시, 선호 태그, 동행자 유형, 시간대를 입력받고 DB에 저장된 공개 대표 코스 중 적합한 결과를 최대 5개 추천한다.

```text
사용자 입력 검증
→ 선택한 도시의 공개 코스 조회
→ 비활성 장소가 포함된 코스 제외
→ 태그·동행자·시간대·인기도 점수 계산
→ 점수순 정렬
→ 앵커 다양성을 고려해 최종 코스 선정
→ 추천 노출 통계 기록
→ 응답 반환
```

### 결정 이유

- 수집·정제된 장소와 검수 가능한 코스만 추천할 수 있다.
- 외부 API 장애와 응답 속도가 실시간 추천에 직접 영향을 주지 않는다.
- 추천된 코스를 먼저 제공하고 사용자가 세부 장소를 수정하는 흐름으로 선택 피로도를 낮출 수 있다.

### 현재 한계

- 추천 품질이 저장된 대표 코스의 수와 품질에 영향을 받는다.
- 사용자 과거 행동을 반영하지 않는 요청 단위 추천이다.
- 코스 생성과 태깅 자동화는 아직 구현되지 않았다.

## 2. 코스와 장소 태그의 통합 평가

### 문제

코스 태그만 평가하면 코스를 구성하는 식당, 카페, 활동 장소의 세부 특성을 놓칠 수 있다. 예를 들어 코스에는 `쇼핑` 태그만 있지만 코스에 포함된 식당에는 `한식` 태그가 있을 수 있다.

### 검토한 방법

1. 코스 태그만 평가
2. 장소 태그만 합산
3. 코스 태그와 장소 태그에서 가장 강한 근거를 사용

태그를 모두 합산하면 같은 의미의 태그가 여러 장소에 있다는 이유만으로 점수가 과도하게 커질 수 있다.

### 결정

사용자가 선택한 태그별로 코스와 구성 장소의 가중치 중 가장 높은 값 하나를 사용한다.

```text
태그별 최종 가중치
= max(코스 태그 가중치, 앵커 및 일정 장소 태그 가중치)
```

최종 추천 점수는 다음과 같이 구성한다.

| 평가 항목 | 최대 점수 | 설명 |
|---|---:|---|
| 태그 적합도 | 70점 | 코스와 장소에서 얻은 태그별 최댓값의 평균 |
| 동행자 적합도 | 10점 | 친구, 연인, 가족 등 요청 조건과의 적합도 |
| 시간대 적합도 | 10점 | 아침, 오후, 밤 요청 조건과의 적합도 |
| 인기도 | 10점 | 기존 코스 선택 횟수 |

요청 태그의 매칭 정도는 `FULL_MATCH`, `PARTIAL_MATCH`, `POPULAR_FALLBACK`으로 구분한다.

### 결정 이유

- 코스의 전체적인 성격과 구성 장소의 세부 특성을 함께 반영할 수 있다.
- 동일 태그의 중복 합산으로 특정 코스가 과대평가되는 것을 방지한다.
- 추천 응답에서 일치·불일치 태그와 점수 구성을 설명할 수 있다.

### 현재 한계

- 태그 및 가중치 품질에 추천 결과가 크게 의존한다.
- 코스 안에서 해당 태그를 가진 장소의 개수와 일정상 중요도는 반영하지 않는다.
- 데이터가 쌓이면 실제 사용자 행동을 기준으로 가중치를 보정해야 한다.

## 3. 인기도 점수와 콜드 스타트

### 문제

사용자가 태그를 적게 선택하면 비슷한 점수를 가진 후보 코스가 많아진다. 선택 횟수를 그대로 점수에 더하면 오래 운영된 코스가 추천 결과를 독점할 수 있고, 신규 코스는 통계가 없어 불리하다.

### 결정

선택 횟수가 증가할수록 최대 10점에 완만하게 가까워지는 포화 함수를 사용한다.

```text
인기도 점수
= selectionCount / (selectionCount + 20) × 10
```

통계가 없는 신규 코스는 선택 횟수를 0으로 계산한다. 노출·조회·선택 비율은 아직 추천 점수에 사용하지 않고 분석용 데이터로만 수집한다.

### 결정 이유

- 선택 횟수가 0이어도 별도 예외 처리 없이 계산할 수 있다.
- 인기 코스를 우대하면서도 인기도가 최대 10점을 넘지 않아 태그 적합도를 뒤집기 어렵다.
- 표본이 매우 적은 코스의 일시적인 높은 선택률이 추천을 왜곡하는 문제를 피할 수 있다.

### 현재 한계

- 누적 선택 횟수만 사용하므로 오래된 코스가 계속 유리하다.
- 노출 대비 선택 성과를 반영하지 않는다.
- 계절성과 최근 인기도 변화를 반영하지 않는다.

### 향후 개선

충분한 노출 데이터가 쌓이면 다음 지표를 검토한다.

```text
상세 조회율 = viewCount / impressionCount
선택률 = selectionCount / impressionCount
상세 조회 후 선택률 = selectionCount / viewCount
저장률 = saveCount / selectionCount
```

표본이 적은 코스가 과대평가되지 않도록 최소 노출 기준, 베이지안 보정 또는 시간 감쇠를 함께 적용한다.

## 4. 추천 결과의 앵커 다양성

### 문제

총점만 기준으로 상위 코스를 선택하면 동일한 앵커를 사용하는 비슷한 코스가 반복될 수 있다.

### 결정

서로 다른 앵커를 가진 코스를 우선 선택하고 결과가 부족할 때만 같은 앵커의 코스로 남은 자리를 채운다.

### 결정 이유

- 추천 점수 구조를 크게 변경하지 않고도 결과의 체감 다양성을 높일 수 있다.
- 같은 도시 안에서 서로 다른 활동 거점을 비교할 수 있다.

### 현재 한계

- 앵커만 다르고 일정 장소 구성이 유사한 코스는 중복으로 판단하지 못한다.
- 지역 및 장소 조합의 유사도를 정량적으로 계산하지 않는다.

## 5. 추천 조회의 N+1 방지

### 문제

추천 점수 계산에는 코스, 앵커, 일정 장소, 코스 태그, 동행자 유형, 시간대가 함께 필요하다. 코스마다 연관 데이터를 개별 조회하면 후보 수에 비례하여 쿼리가 증가한다.

### 결정

- 코스 조회 시 `EntityGraph`로 필요한 연관 데이터를 함께 조회한다.
- 장소 태그는 전체 장소 ID 목록으로 일괄 조회한다.
- 코스 통계는 전체 코스 ID 목록으로 일괄 조회한다.

### 결정 이유

추천 계산 반복문 안에서 추가 조회가 발생하지 않도록 하여 N+1 문제를 방지한다.

### 현재 한계

여러 컬렉션을 한 번에 조회하면 후보가 많아질수록 조인 결과가 커질 수 있다. 실제 성능 문제가 확인되면 코스 ID를 먼저 제한한 뒤 연관 데이터를 분리된 벌크 쿼리로 조회한다.

## 6. 추천 노출 통계의 동시성 처리

### 문제

추천 목록에 포함된 코스의 노출 횟수를 엔티티의 조회-수정-저장 방식으로 증가시키면 동시 요청에서 갱신 손실이 발생할 수 있다.

```text
요청 A: impressionCount 10 조회 → 11 저장
요청 B: impressionCount 10 조회 → 11 저장

기대 결과: 12
실제 결과: 11
```

추천 결과 여러 개를 각각 조회하고 저장하면 불필요한 쿼리도 발생한다.

### 검토한 방법

1. `CourseStats.recordImpression()`으로 엔티티 상태 변경
2. 낙관적 락과 재시도 적용
3. 비관적 락으로 통계 행 잠금
4. DB의 원자적 증가 연산 사용

### 결정

노출 횟수는 별도의 도메인 규칙이 없는 고빈도 집계값이므로 PostgreSQL의 UPSERT와 원자적 증가 연산으로 처리한다.

```sql
INSERT INTO course_stats (course_id, impression_count)
SELECT id, 1
FROM courses
WHERE id IN (:courseIds)
ON CONFLICT (course_id)
DO UPDATE
SET impression_count = course_stats.impression_count + 1;
```

### 결정 이유

- 동시 요청에서도 증가 값이 유실되지 않는다.
- 최종 추천 코스 여러 개를 한 번의 쿼리로 처리한다.
- 아직 통계 행이 없는 코스는 자동으로 생성한다.
- 락과 재시도 코드를 애플리케이션에 추가하지 않아도 된다.

DDD에서 모든 변경을 반드시 엔티티 메서드로 처리해야 하는 것은 아니다. 코스 공개나 일정 추가처럼 도메인 검증이 필요한 행동은 엔티티가 담당하고, 단순 통계 누적은 저장소가 동시성에 안전하게 처리하도록 역할을 나눴다.

### 현재 한계

- 현재 `impressionCount`는 실제 화면 노출이 아니라 추천 API 응답에 포함된 횟수다.
- 기간별 행동 이력을 남기지 않고 누적값만 저장한다.
- 조회·선택·저장·공유 횟수에도 같은 동시성 정책을 적용해야 한다.

### 향후 개선

- 프론트에서 추천 카드가 실제 표시된 시점에 노출 이벤트 전송
- 나머지 행동 카운터도 DB 원자적 증가 방식으로 통일
- 기간별 분석이 필요해지면 집계 테이블과 별도로 행동 이벤트 저장

## 7. 현재 추천 시스템의 범위

현재 구현은 정교한 머신러닝 추천보다 설명 가능하고 검증하기 쉬운 규칙 기반 MVP에 집중한다.

```text
사용자 선호 태그
+ 코스 전체 특성
+ 구성 장소 특성
+ 동행자·시간대 적합도
+ 선택 횟수 기반 인기도
+ 앵커 다양성
```

추천 점수와 매칭 근거를 응답에 포함하여 결과를 확인할 수 있으며, 노출·조회·선택·저장 통계를 축적해 이후 데이터 기반 추천으로 개선할 수 있는 기반을 마련했다.


## 8. 장소 수집 오류 처리와 중단 복구

기록일: 2026-11-16. 구현·검증 작업은 2026-11-13 기준이며, 커밋 `d4f3400`에 오류 처리와 패키지 정리가 포함되어 있다.

### 문제

카카오 → 네이버 → AI → Place 저장 과정은 외부 서비스 호출과 비동기 AI 배치를 포함한다. 인증 오류, 사용량 소진, 매칭 실패, 잘못된 AI 응답은 처리 방법이 서로 다르다. 이를 하나의 오류 코드로 묶으면 재시도 여부와 원인을 파악하기 어렵다. 서버 강제 종료는 catch가 실행되지 않으므로 DB에 처리 중 상태만 남을 수 있다.

AI 배치 안에서 일부 장소만 성공하거나, 결과 일부 저장 후 앱이 종료되는 경우에도 성공한 데이터를 유지하고 미완료 작업을 구분해야 했다.

### 결정

- 단계별 오류 핸들러: 카카오·네이버·AI의 오류 해석과 실패 처리 진입점을 모은다.
- 공통 분류기: 원인 예외, HTTP 상태, 명시적 외부 오류 정보를 수집 오류 코드로 변환한다.
- 공통 정책: 재시도 가능 여부와 다음 실행 시각을 결정한다.
- Writer: 상태·오류·재시도 시각을 짧은 트랜잭션으로 저장한다.
- 복구 스케줄러: DB에 예약된 실행 가능 대상을 찾아 단계 서비스를 호출한다.
- 시작 복구: 단일 수집 인스턴스 조건에서 중단 작업의 상태를 정리한다.

```text
단계 서비스에서 예외 발생
→ 단계별 ErrorHandler
→ CollectionFailureClassifier: 원인 분류
→ Writer: 실패 저장
   → CollectionErrorPolicy: 다음 재시도 시각 결정
→ 예약 시각 이후 Scheduler가 대상 조회
→ 같은 단계 서비스 재실행
```

HTTP 응답을 만드는 GlobalExceptionHandler와 내부 수집 작업의 오류 처리는 역할을 분리했다.

### 중요한 구현

- 카카오 구역 분할 시 부모 상태와 자식 구역 전체를 한 트랜잭션에 저장한다. 페이지별로 저장한 Temp는 유지하고, 중단 구역은 1페이지부터 다시 조회하되 공급자 ID로 중복을 방지한다.
- 네이버는 장소 단위로 선점·완료·실패를 저장한다. 주소만 같고 이름이 다른 후보를 자동 확정하지 않는다. 블로그 조회 실패는 별도 기록하고 장소 정제는 진행한다.
- AI는 제출 당시 공급자·모델과 요청별 대상 ID 목록을 저장한다. 결과 반영 처리권과 장소별 완료 기록을 통해 동시 수집과 완료 결과 재반영을 방지한다.
- AI 한 장소의 저장은 Place·PlaceTag·Temp·결과 반영 기록이 함께 성공하거나 롤백된다. 다른 장소는 계속 처리할 수 있다.
- 종료된 원격 배치에서도 회수 가능한 성공 결과를 먼저 저장한다.
- AI 일반 오류는 짧은 재시도 3회 이후 24시간 간격으로 재시도한다. 사용량 소진은 신뢰할 수 있는 초기화 시각이 있으면 이를 사용하고, 없으면 24시간 뒤로 예약한다.
- 인증·잘못된 요청과 원격 접수 여부 불명은 무조건 재제출하지 않는다. 진행 중인 원격 배치도 경과 시간만으로 실패 처리하지 않는다.

### 검증과 한계

당시 전용 PostgreSQL 테스트 DB에서 전체 117건 중 116건 통과, 실제 모델 호출 테스트 1건 생략을 기록했다. DB 저장 실패, 부분 반영 후 재수집, 처리권 경쟁, 구역 분할 롤백 등을 장애 주입으로 확인했다. 이후 패키지 이동에서는 main/test 소스 컴파일을 확인했다.

실제 운영 서버 강제 종료 실험, OmniRoute 프로세스 재시작 후 배치 재개, 실제 오류 결과의 초기화 시각 전달까지 검증한 것은 아니다. 해당 결과를 검증 완료로 표현하지 않는다. 세부 내용은 [통합 가이드](./place-collection/GUIDE.md), [변경 보고서](./place-collection/CHANGE_REPORT.md)에 남겼다.

## 9. 수집 코드를 기능별 패키지로 정리

### 문제와 결정

테스트 진입점을 기준으로 생긴 batch/common 하위에 동일한 단계의 코드가 나뉘어 있어 실행과 오류 처리 위치를 찾기 어려웠다. pipeline 아래를 기능별로 정리했다.

```text
pipeline/
├── kakao/          카카오 수집

├── ai/             AI 제출·결과 반영
├── orchestration/  단계 연결·시작 복구
├── scheduler/      주기 실행 진입점
├── support/error/  수집 전용 오류 정책
└── test/           수동 테스트 컨트롤러
```

테스트 컨트롤러의 카카오 → 네이버 → AI 제출 호출은 PlaceCollectionOrchestrator.runArea()로 옮겼다. 기존 API 경로와 응답은 유지했다. 수집 전용 오류 정책은 pipeline에, HTTP 공통 오류 응답은 global/exception에 둔다.

## 10. DB 상태 기반 4단계 병렬 파이프라인 설계

기록일: 2026-11-16. 최초 기록은 설계 단계이며, 이후 구현·동시성 검토 진행은 아래 11절에 기록한다.

### 기존 구조에서 확인한 점

통합 테스트의 runArea()는 카카오 수집이 반환된 뒤 네이버 정제를 실행하고, 그다음 AI 배치를 제출한다. AI 결과 수집은 별도의 주기 작업이다. 카카오가 수집한 앞쪽 장소도 해당 호출이 끝나기 전까지 이 통합 실행 경로의 네이버 단계로 넘어가지 못한다.

별도 스케줄러 실행 풀 설정도 없어 기본 스케줄러에서 긴 작업이 다른 주기 작업을 지연시킬 가능성을 확인했다. 이는 코드 분석으로 발견한 예상 병목이며, 실제 성능 저하를 측정한 결과는 아니다.

### 선택한 방향

네 단계에 전용 실행 스레드를 하나씩 배정하고 DB 상태를 단계 사이의 대기열로 활용한다. 같은 장소는 순서를 지키지만 서로 다른 장소는 네 단계에서 동시에 처리한다.

```text
① 카카오: 실행할 구역 Job → 원본 Temp 저장
    ↓ NAVER_ENRICHMENT / PENDING
② 네이버: 대기 Temp → 매칭·블로그 보강
    ↓ AI_TAGGING / PENDING
③ AI 제출: 대기 Temp 묶음 → 원격 Batch 제출
    ↓ AI Job / SUBMITTED
④ 결과 수집: 원격 상태 확인 → 완료 결과 Place·PlaceTag 저장
    ↓ AI_TAGGING / COMPLETED
```

초기에는 카카오만 처리하다가 앞 단계의 결과가 저장되면 다음 단계가 이를 가져간다. 각 worker는 주기적으로 제한된 작업을 처리하고 반환한다. AI 완료까지 스레드를 붙잡고 기다리거나 빈 대기열을 무한 반복 조회하지 않는다.

### 선택 이유

- 카카오·네이버 API와 비동기 AI의 처리 속도가 서로 다르므로 단계별로 독립 진행할 수 있다.
- 전체 Area 수집 완료를 기다리지 않고 먼저 저장된 장소부터 다음 단계에서 처리할 수 있다.
- DB의 상태와 예약 시각을 재사용해 재시작 후 미완료 작업을 찾는다.
- 기존 Job·Temp·Writer·오류 정책을 활용할 수 있다. Spring Batch나 별도 메시지 브로커 도입은 현재 구조의 한계가 확인될 때 재검토한다.

### 구현 전 확정할 정책

| 항목 | 현재 논의 상태 |
|---|---|
| 단계 실행 | 단계별 전용 실행 스레드 1개 방향 합의 |
| 일일 신규 작업 | 수집할 Area 수·선정 방식·시각 미정 |
| 일일 작업 중복 방지 | 날짜·Area 기준 작업 등록 중복 방지 및 놓친 일정 복구 필요 |
| API 호출량 | 공급자별 속도·일일 예산 설정 필요. 장소 수와 호출 수는 다름 |
| AI 제출 단위 | 기존 요청당 최대 10개, Job당 최대 1,000개 유지. 최소 제출량·최대 대기 시간은 미정 |
| 대기량 제한 | 뒤 단계가 밀리면 앞 단계 실행을 보류하는 상한 필요 |
| 공급자 장애 | 인증 오류·한도 소진 시 같은 공급자 요청을 연속 발생시키지 않는 실행 보류 필요 |

앞서 제시한 worker 실행 간격 30~60초, 네이버 50~100개, AI 100개 또는 10분 대기 기준은 검토 예시이며 확정된 운영값이 아니다.

### 현재 코드에서 연결할 작업

- 카카오 신규 수집 일정을 등록하고 기존 구역 복구 흐름과 연결한다.
- 네이버는 기존 복구 대상뿐 아니라 신규 PENDING을 처리한다.
- AI는 기존 실패 재제출·결과 조회 외에 신규 PENDING 자동 제출을 연결한다.
- 단계별 실행 자원, 중복 실행 방지, 처리량·대기량 제한을 설정한다.
- 운영 파이프라인은 DB 상태로 단계를 연결하고 수동 통합 테스트 진입점은 별도로 유지한다.

### 이후 검증할 내용과 경력 정리 기준

병렬 구현 후 같은 입력과 고정 지연의 모의 외부 API로 순차·병렬 실행을 비교한다. 전체 완료 시간, 단계별 처리량·대기량, API 호출 수, 오류율, CPU·메모리를 기록하고 실제 외부 API 실험과 구분한다. 부분 실패와 서버 중단 후 복구도 확인한다.

현재 사실에 맞는 설명은 “운영 스케줄링 설계 중 코드 분석으로 단계 간 대기와 기본 스케줄러의 지연 가능성을 확인하고, DB 상태 기반 병렬 파이프라인을 설계했다”이다. 순차 운영에서 장애를 관측했다거나 성능을 몇 배 개선했다는 경험·수치는 아직 없다. 구현·측정 후 이 기록을 갱신한다.

## 11. 전용 스케줄러 연결 및 운영체제 동시성 개념으로 검토

기록일: 2026-11-16. 상태: 실행 경로 연결·컴파일 확인, 동시성 위험 보완과 재현 검증은 진행 예정.

### 구현한 내용

- ThreadPoolTaskScheduler Bean 네 개를 만들고 각각 poolSize=1로 설정했다. 카카오, 네이버, AI 제출, AI 결과 수집 작업에 전용 스케줄러를 지정했다.
- 네이버 worker는 refinePending(100)을 호출한다. 신규 PENDING과 재시도 가능한 FAILED를 함께 처리한다.
- AI 제출 worker는 submitPending(1000)을 호출한다. 신규와 재시도를 하나의 제출 경로에서 처리한다.
- AI 결과는 findPollableJobs로 회당 최대 5 Job을 조회한다. 자동 조회 제외 오류와 유효한 수집 lease가 있는 Job을 DB에서 제외하고, 미조회·오래된 조회 시각·ID 순으로 선택한다.
- AI 수집권 선점 UPDATE에서 last_polled_at도 기록해 통신 실패 시에도 다른 Job에 조회 기회가 돌아가도록 했다.
- 스케줄러의 :60000 기본값을 제거하고 실행 주기를 application.yaml에서 관리한다.
- 카카오의 신규 일일 Area 등록 정책은 아직 구현하지 않았다. 현재는 기존 구역의 실행·복구를 수행한다.

### 동시성을 다시 검토하게 된 배경

운영체제에서 concurrency, critical section, lock, condition variable, semaphore를 학습하면서, 네 단계가 병렬 실행될 때 공유 데이터 변경이 안전한지 질문했다. 전용 스레드 하나가 해당 단계의 예약 실행을 직렬화하더라도 다른 단계·수동 API와의 동시 접근까지 막지는 못한다는 점을 확인했다.

공유 자원은 주로 DB의 Job·Temp·Place 행이다. 현재 코드는 FOR UPDATE/PESSIMISTIC_WRITE, 조건부 UPDATE에 의한 선점, 짧은 Writer 트랜잭션, AI collect_token/lease를 사용한다. 외부 API 응답을 기다리는 동안 장시간 DB 잠금을 유지하는 대신 PROCESSING 상태 또는 수집권을 저장한다. 단계 간 전달은 condition variable로 통지하는 방식이 아니라 커밋된 DB 상태를 주기적으로 조회하는 방식이다.

### 코드 분석으로 찾은 보완 대상

| 항목 | 위험과 보완 방향 | 검증 상태 |
|---|---|---|
| 시작 복구와 예약 실행의 순서 | ApplicationRunner 복구와 @Scheduled 작업 사이에 명시적인 완료 대기가 없다. 시작 복구가 새 작업의 상태·수집권을 변경할 가능성을 막도록 복구 완료 후 예약 작업을 허용한다. | 코드 분석, 시작 경쟁 재현 미실시 |
| 즉시 태깅 테스트와 배치 제출 경쟁 | AiTaggingTempWriter.startPending의 다건 대상 조회에 행 잠금이 없다. 배치 claim과 같은 Temp를 동시에 선점할 가능성이 있어 조회·선점을 원자적으로 보호한다. | 코드 분석, 경쟁 재현 미실시 |
| 카카오 재수집과 후속 분류의 공유 필드 | refreshKakao와 네이버·AI가 defaultPlaceType을 함께 변경한다. DynamicUpdate는 변경 열만 갱신하지만 같은 열의 덮어쓰기는 막지 못한다. 후속 단계 진입 후 원본 갱신이 분류 결과를 되돌리지 않도록 필드 갱신 정책과 동시 저장을 검토한다. | 코드 분석, 덮어쓰기 재현 미실시 |

이 항목들은 확인한 코드 경로의 위험이며 실제 운영 장애가 발생했다고 기록하지 않는다. 행 잠금만 추가하면 모든 문제가 해결된다고 가정하지 않고, 상태 전환·처리권·락 획득 순서까지 함께 점검한다.

### 사용자가 직접 진행할 작은 작업 순서

1. 시작 준비 상태를 공유하는 작은 컴포넌트를 만들고 ApplicationReadyEvent 이후 worker 실행을 허용한다. ready 이전의 모든 예약 메서드는 반환한다. 기존 ApplicationRunner 복구가 성공한 뒤에만 준비 완료가 되도록 한다. 스레드 사이 가시성을 위해 volatile/AtomicBoolean 등을 사용하고, 스케줄러 스레드를 sleep으로 대기시키지 않는다.
2. 즉시 태깅 startPending과 배치 claim의 대상 선점이 동일한 Temp 행 잠금 규칙을 따르게 한다. 기존 상태 조건을 유지하고 동시 선점 검증을 추가한다.
3. 카카오 원본 갱신과 후속 단계 분류가 공유하는 defaultPlaceType의 갱신 범위를 정하고, 동시 실행에서 분류가 되돌아가지 않도록 수정·검증한다.
4. 각 수정 후 작은 단위로 검증한다. 시작 복구 전 worker 미실행, 준비 후 실행, 한 Temp 중복 선점 방지, 원본 재수집 중 분류 보존을 확인한다.
5. 이후 일일 카카오 수집 정책과 공급자별 처리량·대기량 상한 설계로 돌아간다.

### 이번 확인 범위

Java 21 환경에서 ./gradlew compileJava --offline 통과. 실제 외부 API 호출, DB에서 새 조회 쿼리 실행, 위 세 경쟁 상황의 장애 주입·재현은 이번 검토에서 수행하지 않았다. 따라서 병렬 수집 운영 검증 완료로 판단하지 않는다.


## 12. 초기 구축 스케줄링 방향과 검증 기록 갱신 (2026-11-16)

초기 구축 등록과 운영 등록 스케줄러를 분리하고, 카카오·네이버·AI 제출·결과 worker 4개는 공통 사용하기로 했다. 초기에는 공급자 예산 안에서 서울을 순회하고 소진 시 대기·초기화 후 재개한다. 하루 Area 수·03시 실행·rank 순서는 확정하지 않았다. YAML mode=INITIAL만 추가됐으며 신규 등록과 예산 제어는 아직 미구현이다.

이전 11절의 “즉시 startPending 조회에 잠금이 없다”는 분석을 정정한다. Repository에 PESSIMISTIC_WRITE가 이미 존재한다. 격리 PostgreSQL 17 임시 컨테이너에서 복구 통합 테스트 11개와 scheduler 단위 테스트 1개가 skip 없이 통과했고, 즉시/Batch 중복 선점 검증을 포함했다. 개발 DB를 사용하지 않았고 임시 컨테이너는 종료했다.

ApplicationReadyEvent 이후 예약 작업을 허용하는 readiness guard를 구현했다. 실제 시작 경쟁 장애 주입까지 확인한 것은 아니다. refreshKakao는 NAVER_ENRICHMENT에서만 defaultPlaceType을 갱신하도록 수정했고 PlaceCollectionTempTest 7개가 통과했다. 전체 테스트 모음과 전체 초기 구축은 검증하지 않았다.

[공동 구현 계획](./place-collection/scheduling-implementation-plan.md)을 최신 합의로 재작성했다. 다음 학습 단계는 초기 구축 한 회차와 Area·프로필 대상 이력의 최소 저장 구조를 함께 설계하는 것이다. API 예산·페이지 이어받기·신규 등록·대기량 제어·전체 종료 집계를 작은 단위로 구현한다. 카카오 SPLIT 부모는 자식 결과로 판단하며 카카오 순회 완료와 Place 구축 완료를 구분한다. 운영 모드 정책은 추후 논의한다.


## 13. 정책 기반 초기 수집 스케줄링 재구성 (2026-11-16)

사용자 합의로 scheduling/config·policy·scheduler·service와 budget 패키지로 재구성했다. 초기/운영 정책을 교체하는 CollectionPolicy를 도입하고 INIT는 서울 Area ID순으로 미등록 대상을 선정한다. 기존 4개 전용 스레드는 새 Config에서 생성하며 기존 pipeline/scheduler 클래스는 제거했다.

새 Area는 잠금 후 기존 Job을 재확인하고 활성 프로필 root를 원자적으로 등록한다. 실제 검색·정제·배치 저장/오류 정책은 pipeline 서비스를 재사용한다. 카카오 페이지 체크포인트와 초기 회차/대상 테이블은 추가하지 않는다.

카카오·네이버의 독립 main/team 인증 정보를 구성하고 실제 소진 응답에 따라 다음 키로 동일 요청을 보낸다. 키 상태 저장용 V15 테이블 하나를 추가했다. 네이버는 API HUB 월간 검색 공통 scope, 카카오는 검색 종류별 일간 대기를 사용한다. 알 수 없는 429는 짧은 cooldown, 인증 오류는 수동 확인 대상으로 구분했다. 예산 정상 대기는 카카오 READY/네이버 PENDING과 nextRetryAt에 저장하고 이번 시도 횟수를 돌려놓는다. 시작 복구가 READY 대기 시각을 지우지 않도록 수정했다.

03시 이후 신규 처리를 허용하고 AI 결과는 시간/제출 상한과 독립적으로 회수한다. 대기량 상한과 AI 동시 배치 상한을 설정으로 관리한다. 자동 수집은 기본 OFF다. 개발 DB 초기화와 실제 계정 키를 사용한 수집·AI 호출은 수행하지 않았다. 구조와 운영 방법은 [스케줄링 가이드](./place-collection/scheduling-guide.md)에 기록했다.

검증 결과: 임시 PostgreSQL 17의 course_recovery_test에서 전체 테스트 136개 중 135개 통과, 실제 OmniRoute 호출 테스트 1개는 의도적으로 skip, 실패/오류 0개. Flyway V15 적용, enabled=true 예약 메서드 4개 등록, HTTP 레벨 키 전환, 카카오 페이지 대기 후 첫 페이지 재개(요청 페이지 1→2→1), 정상 대기 복구, AI 부분 결과 저장/복구를 확인했다. git diff --check도 통과했다. 실제 공급자 한도 소진과 전체 서울 장기 실행은 미검증이다.


## 14. pipeline의 수동 테스트 경로 제거와 결과 Writer 통합 (2026-11-16)

스케줄링 재구성 뒤 pipeline에 수동 실행 API/Orchestrator/즉시 AI 경로가 남아 구조를 읽기 어려웠다. 호출부를 확인해 수동 Controller 5개, 순차 Orchestrator, 전용 DTO, 즉시 AI 서비스·Temp Writer·HTTP 클라이언트를 제거했다. 카카오 collectCity/collectArea/initialize 및 네이버 중복 재시도·Area 한정 처리 진입점, AI 수동 제출·재태깅 진입점도 정리했다. 신규 Job 등록은 CollectionJobRegistrationService로 모았다. pipeline Java 파일 수는 51개에서 36개로 감소했다.

두 AI 결과 Writer를 AiBatchResultWriter 하나로 합치며 소유권/manifest/Temp 잠금과 Place·태그·완료 기록을 같은 트랜잭션으로 유지했다. 오류 처리·롤백·부분 성공 저장은 보존했다. 복구 클래스는 scheduling/service/CollectionRestartRecovery로 이동했다. 즉시/배치 동시 선점 테스트는 실제 남은 배치 제출 간 경쟁 테스트로 전환했다. 삭제된 기능의 테스트는 제거하고 결과 검증 테스트는 통합 Writer로 이전했다.

격리 PostgreSQL 17 course_recovery_test에서 전체 테스트 132개 중 131개 통과, 실제 OmniRoute 호출 테스트 1개 skip, 실패/오류 0개. 새 마이그레이션이나 DB 삭제는 수행하지 않았다. 자동 수집 기본 OFF를 유지하고, 수동 수집 API 제거 사실을 최신 가이드에 명시했다.
